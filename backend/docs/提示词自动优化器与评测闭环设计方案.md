# 提示词自动优化器与评测闭环 —— 设计方案

> 状态：待评审 | 前置依赖：Prompt 实验室（版本管理 + 评测集）已上线
> 目标读者：本项目开发者 | 涉及范围：backend / frontend

---

## 一、背景与现状

ResourceHub 的 Prompt 实验室目前已经具备两块能力：

| 已有能力 | 实现位置 | 说明 |
|---|---|---|
| 版本管理 | `PromptVersion`（`app/models/prompt.py`） | git 式版本：version_number / branch_name / labels / commit message |
| 评测集 | `PromptEvalSuite / PromptEvalCase / PromptEvalResult`（`app/models/ai.py`） | 用例（变量 + 期望输出 + 评分细则）→ LLM-as-judge 0-100 打分 |
| 评测执行 | `app/services/ai/eval_service.py` | 逐用例生成 + 评委打分，返回 avg_score / latency / tokens |
| 用量配额 | `ensure_quota` + `record_usage` | 单用户每日 token 上限 |

**当前痛点：** 评测能告诉我们"这个版本得了 78 分、第 3 个用例的扣分理由是 XX"，但**改提示词仍然全靠人肉**。用户看到低分和 judge_reason 之后，要自己回编辑器琢磨怎么改，改完再手动跑一轮评测对比——闭环断在"分析 → 改写"这一环。

## 二、要做什么（目标）

**提示词自动优化器（Prompt Auto-Optimizer）**：以评测结果为输入，由 AI 自动完成"分析失败原因 → 生成改进候选版本 → 重新评测对比 → 给出采纳建议"的完整闭环，用户全程只需要做一件事——**点采纳，或者不点**。

一句话定义闭环：

```
基线评测 → AI 诊断低分用例 → 生成候选提示词 → 候选评测 → 分数对比
     ↑                                                    │
     └────────── 不满意则继续迭代（最多 N 轮）←──────────────┘
                              ↓ 满意
                    用户采纳 → 自动落一条新版本（带 commit message）
```

**明确不做的事（防止范围膨胀）：**

- 不做多模型对比/Arena——已有评测体系足够，优化器只聚焦"提升单个提示词"
- 不做无人工确认的自动替换 production 标签——AI 只能建议，采纳永远由用户点击
- 不做自动生成评测集——复用用户已有的评测集（该能力可作为后续独立功能）

## 三、核心设计

### 3.1 优化会话（OptimizationRun）状态机

一次"自动优化"是一个可追溯的会话实体，而不是一次性的函数调用：

```
running ──→ awaiting_review（本轮候选已出分，等用户决策）
   │                  │
   │            ┌─────┴──────┐
   │         采纳 ↓           ↓ 继续迭代（budget 还有）
   │        completed ──→ running（下一轮）
   │            │
   │      用户放弃 ↓
   └──→ cancelled    failed（调用/评测异常）
```

关键规则：

- **budget 控制**：`max_rounds`（默认 3）与 `AI_DAILY_TOKEN_QUOTA` 双重限制，每轮 = 1 次诊断改写调用 + len(cases) × 2 次调用（生成 + 评委）
- **防漂移**：诊断改写的 prompt 中强制要求"保留原提示词的全部变量占位符与结构语义，只做针对性改进"，并在后端做 `variables` 集合一致性校验（候选丢失变量 → 本轮作废，标记 skipped）
- **评委一致性**：候选与基线必须用同一个 judge_model 和同一套 cases 打分，对比才成立（沿用 suite.judge_model）

### 3.2 每轮内部的四步流水线

| 步骤 | 输入 | AI 调用 | 输出 |
|---|---|---|---|
| 1. 基线快照 | 当前版本内容 + suite | 无（复用 `eval_service.run`） | baseline avg_score / 逐用例 judge_reason |
| 2. 诊断改写 | 低分用例（score < 阈值，默认 80）的 output + judge_reason + 原文 | 1 次结构化输出（JSON：`analysis` / `improved_content` / `changelog`） | 候选提示词 + 改动说明 |
| 3. 候选评测 | 候选内容 + 同一 suite | 复用 `eval_service.run`（传入 candidate 内容而非 DB 版本） | candidate avg_score |
| 4. 对比报告 | 两个 avg_score + 逐用例分差 | 无（纯计算） | delta、逐用例升降清单、采纳建议文案 |

> 实现注记：`eval_service.run` 目前从 DB 读版本内容，需要小幅重构——把 `_resolve_content` 抽出"内容来源"参数（DB 版本 ID 或直接传字符串），优化器复用时传候选字符串。这是唯一需要动的现有代码。

### 3.3 数据模型（新增 2 张表）

```python
class PromptOptimizationRun(Base):
    __tablename__ = "prompt_optimization_runs"

    id, prompt_id, suite_id          # 归属
    user_id                          # 配额归属
    status                           # running / awaiting_review / completed / cancelled / failed / skipped
    round_number                     # 当前第几轮（从 1 起）
    max_rounds                       # 本次会话允许的最大轮数
    baseline_version_id              # 基线版本（可空 → 用当前 content）
    baseline_score                   # 基线均分（JSON 快照里也有逐用例明细）
    candidate_content                # 当前轮候选内容（Text）
    candidate_score                  # 候选均分
    candidate_version_id             # 采纳后落地的新版本 ID（可空）
    analysis                         # 本轮 AI 诊断文本
    changelog                        # 本轮改动说明（未来直接作为 commit message）
    snapshot                         # JSON：逐用例对比明细（case_id / baseline / candidate / delta / 两条 judge_reason）
    error_message                    # failed 时的原因
    created_at / updated_at

class PromptOptimizationRound(Base):
    __tablename__ = "prompt_optimization_rounds"

    id, run_id, round_number
    candidate_content / candidate_score / analysis / changelog
    snapshot                         # 本轮逐用例对比 JSON
    total_tokens                     # 本轮消耗（供配额与成本展示）
    created_at
```

- `Run` 存"当前状态"，`Round` 存"每一轮历史"——用户可以翻看第 1/2/3 轮分别改了什么、涨了多少分
- 均分等聚合值直接落列，避免前端反解 JSON

### 3.4 API 设计（挂在现有 `/ai` 或 `/prompts` 前缀下）

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/ai/prompt-optimizer/runs` | 启动优化会话。body: `{prompt_id, suite_id, prompt_version_id?, max_rounds?, score_threshold?}`。后台任务执行第 1 轮 |
| GET | `/ai/prompt-optimizer/runs/{run_id}` | 轮询会话状态 + 当前轮进度（SSE 可选，先做轮询，复杂度最低） |
| POST | `/ai/prompt-optimizer/runs/{run_id}/iterate` | awaiting_review 状态下继续下一轮 |
| POST | `/ai/prompt-optimizer/runs/{run_id}/accept` | 采纳候选 → 写入 `PromptVersion`（version_number+1，changelog 作为 message，labels 继承基线）→ run 置 completed |
| POST | `/ai/prompt-optimizer/runs/{run_id}/cancel` | 取消 |
| GET | `/ai/prompt-optimizer/runs/{run_id}/rounds` | 历史轮次列表 |

后台执行方式：`asyncio.create_task` + 进度落库（status / round_number），与现有 `agent_service` 的运行恢复思路一致，不引入 Celery 等新依赖。

### 3.5 前端交互（Prompt 实验室内新增"自动优化"页签）

- 入口：提示词详情 → 实验室区域新增第三个面板 `OptimizePanel.vue`（与 VersionHistoryPanel / UsageAnalyticsPanel 并列）
- 配置表单：选评测集、最大轮数、低分阈值 → 点击"开始优化"
- 运行态：轮次进度条 + 当前步骤高亮（诊断中 / 评测中）+ token 消耗实时累计
- 审查态（awaiting_review）核心 UI：
  - 顶部对比卡：基线 78 分 → 候选 86 分（+8，绿色/红色分色）
  - 左右双栏 diff 视图（候选与原文，用现有 markdown 渲染 + 简单行级 diff 即可，不引入 diff 库）
  - 逐用例折叠列表：每条显示两个 judge_reason 与分差
  - 三个按钮：**采纳为新版本**（主按钮）/ **再优化一轮**（budget 剩余时可用）/ **放弃**
- 采纳成功后 toast 引导跳转到版本历史，让用户看到自动生成的 commit message

## 四、执行步骤（建议按此顺序实现，每步可独立验证）

### 阶段 0：准备（0.5 天量级）
1. `eval_service.py` 重构：`_resolve_content` 支持"直接传入内容字符串"，现有评测接口行为不变（回归 `uv run pytest`）
2. `app/schemas/ai.py` 增加 optimizer 相关 schema；`app/models/ai.py` 增加上述 2 张表
3. Alembic 迁移：`uv run alembic revision --autogenerate -m "add prompt optimization tables"` → `uv run alembic upgrade head` → `uv run alembic check`

### 阶段 1：后端优化器服务（核心）
4. 新建 `app/services/ai/optimizer_service.py`：
   - `start_run()`：校验 suite/prompt 归属与配额 → 建 Run → 起 asyncio 后台任务
   - `_run_round()`：实现 3.2 的四步流水线，每步落库进度；诊断改写用 `AI_FAST_MODEL`，输出强制 JSON（复用 `_parse_judge` 的解析思路）
   - 变量一致性校验 + 失败置 skipped 的逻辑
   - `iterate / accept / cancel / get_status`
5. `accept` 落版本时复用 prompts 路由现有的建版本逻辑（抽公共函数或直接调用 service）
6. `app/routers/ai.py` 注册 6 个端点，全部走 `get_current_user` + `ensure_quota`
7. 测试：`tests/` 新增 optimizer 测试（mock provider，覆盖：正常一轮采纳、两轮迭代、变量漂移 skipped、token 超额 failed、cancel）

### 阶段 2：前端
8. `frontend/src/api/` 新增 optimizer API 模块
9. 新建 `frontend/src/components/prompts/OptimizePanel.vue` + 行级 diff 小工具（可先用最简单的按行 LCS diff，约 40 行，不引依赖）
10. 提示词详情页挂载新面板；轮询 `GET runs/{id}`（2s 间隔，running 时）

### 阶段 3：打磨与演示
11. 对比报告的采纳建议文案（如"候选在 5 个用例中 4 升 1 平，建议采纳"）
12. token 消耗展示 + quota 不足的友好报错
13. 全链路联调：真实跑一个低分提示词走完"评测 → 优化 → 采纳 → 新版本出现在历史里"

### 验收标准
- [ ] 一个 avg_score 70 分左右的提示词，3 轮内优化器能给出 +5 分以上的候选（取决于模型，不强求）
- [ ] 采纳后版本历史出现新版本，message 为 AI changelog，variables 与原版一致
- [ ] 每轮 token 消耗被记录且计入每日配额
- [ ] 变量漂移、provider 异常、配额耗尽三种异常均正确落终态且 UI 可见

## 五、风险与对策

| 风险 | 对策 |
|---|---|
| 评委打分抖动，候选涨分可能是噪声 | 对比时同 judge_model + 同 cases；报告里展示逐用例明细而非只给均分；后续可加"关键用例复评一次" |
| AI 改写丢变量/改坏结构 | 后端 variables 一致性硬校验，不通过则本轮 skipped |
| token 成本失控 | max_rounds 默认 3 + ensure_quota 每轮前置检查 + 前端实时显示消耗 |
| 后台任务进程重启丢失 | Run 状态落库，重启后 running 超时的 run 标记 failed，用户可重新发起（与 agent 恢复策略一致） |

## 六、给比赛展示的加分点

- **完整闭环叙事**：评测不是终点而是优化器的输入——"AI 管理自己的提示词"是天然的故事线
- **全程可追溯**：每一轮的 diff、分数、理由都落库可回放，演示时翻轮次历史就是最好的 demo
- **人机边界清晰**：AI 出建议、人做决策，答评委"为什么不让 AI 直接改"有现成答案（可控性 + 防漂移设计）
